## 二、v1.2 增补 · 原型与美术对齐（热区 / 构图）

### 2.1 单一事实源（Single Source of Truth）

| 层级 | 职责 |
|------|------|
| **玩法状态机** | `baking.js` / `collection.js` / `game.js` 等为权威：有哪些阶段、哪些可点。 |
| **输入热区** | `input.js` 中的矩形必须与**最终静帧或程序矢量 UI**一致；静帧图改构图时以热区为准反向改图。 |
| **表现层** | `renderer.js`：静帧铺满内容区时，矢量 UI 不得与静帧在**同一语义**上重复（例如两套顾客）。 |

### 2.2 静帧资源规范（交付到 `assets/`）

- 每个场景 **横屏 16:9** 与 **竖屏 9:16** 各一帧时：须在画中预留 **安全区**（底部导航约 72dp、顶部状态区约 64dp），避免假按钮与程序按钮叠映。  
- 烤鱼店静帧：  
  - **加火 / 翻面** 与程序 QTE 同义时，画中「可操作建议」必须落在 **`input.js` 厨房热区** 内，或去掉独立假按钮，只保留烤架区域暗示。  
  - **成品区**：需在柜台或传餐口留出空位，与 `drawReadyGoods` / `drawPlating` 飞入目标一致。  
  - **顾客区**：静帧已画排队动物时，程序层应**关闭**重复的矢量顾客卡片（`artOn` 时仅以静帧为准或仅保留订单气泡）。  
- 钓鱼静帧：海面**不得绘制当前逻辑不会出现的鱼种**作为「可钓暗示」；装饰鱼种集合须与 `rollFishSpecies` 可出池一致（见下节）。

### 2.3 钓鱼「所见即所得」

- **展示用鱼种**（水面游动、示意）必须从与 **当前钓点 + 等级/解锁** 一致的池子中选取。  
- **禁止**：浅滩阶段画面出现金枪鱼 / 金色传说等而概率表根本不出。  
- **允许**：无鱼或少鱼氛围（仅用气泡、波纹），优先于错误鱼种展示。

### 2.4 订单与产出一致

- 顾客订单中的鱼种必须 **当前可钓或可库存获得**；禁止订单要求未解锁钓点专属鱼种。  
- 订单生成与 `rollFishSpecies` / 库存规则共用同一套**可订单白名单**。

## 三、v1.2 增补 · 迭代纪律

### 3.1 横竖屏

- v1.1 中「横屏 16:9」扩展为：**横屏与竖屏均为正式目标**；验收用例需在两种朝向下各执行一轮关键路径（地图 → 钓鱼/椰林 → 建店 → 烤鱼店核心操作）。

### 3.2 单问题最多 3 次修复尝试

- 针对**同一 bug 编号/同一根因**，自主修复最多 **3** 轮（改代码 → 自检 → 对照 Rubrics）。  
- **3 轮仍失败**：停止该条自动修复，记录失败原因与尝试差异，**上报人工**；不得为通过验收而降级为「掩盖型 workaround」除非人工同意（与 v1.1 修改边界一致）。

### 3.3 与生图流水线协作

- 静帧迭代须**保持画风**（治愈系手绘 + 轻度像素）；构图变更以本节 2.x 为准。  
- 生图工具不可用或无法访问内网 API 时：**复制现有引擎资源与设计文档引用到 `assets/`**，并撰写 `assets/ART_COMPOSITION_NOTES.md` 说明与热区的对齐关系，不阻塞程序修复。
