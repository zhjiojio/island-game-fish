# 斗地主服务端生产环境问题、挑战与解决方案

> 项目：老铁斗地主（APPID：`ks699465320497476962`）  
> 文档状态：生产就绪评审稿  
> 更新时间：2026-08-18  
> 适用范围：生产上线评审、安全评审、稳定性治理、容量规划、发布运维和事故响应

## 1. 背景与结论

当前本地开发运行正常，只能说明核心功能链路基本成立。真正进入生产环境后，还要面对公网网络、长连接、并发事务、实例故障、攻击、发布、观测、备份、成本和人员协作等问题。

结合当前实现，最重要的结论是：

> 当前代码可以通过生产化改造后上线，但现阶段只能采用单活动游戏实例。生产化重点不是简单增加机器，而是先补齐健康检查、优雅关闭、MySQL 并发验证、资金补偿、密钥、监控、发布和恢复体系。

风险按优先级分为：

- **P0 上线阻塞**：正式上线前必须解决，否则可能无法访问、数据错误或无法安全恢复；
- **P1 正式放量**：小流量运行前后必须补齐，否则容易在流量和故障下失稳；
- **P2 长期演进**：用于提高可用性、降低运维成本和支持规模增长。

---

## 2. 当前系统的生产边界

当前服务端采用 Node.js + `ws`，并使用服务端权威游戏状态。账户、钱包、流水和比赛记录可持久化到 MySQL，但以下状态仍位于单个进程内存：

- 房间与进行中牌局；
- 匹配队列与匹配会话；
- 加入预约与一次性票据；
- WebSocket 连接；
- 行动、断线和机器人计时器；
- 进程内限流桶；
- 平台 session key 缓存。

这意味着：

1. 当前只保证单活动进程正确；
2. RDS 高可用不等于牌局高可用；
3. 进程重启会丢失进行中的牌局；
4. 不能直接将两台 ECS 同时以正常权重加入 ALB；
5. 粘性会话不能替代房间归属和分布式一致性；
6. 所有环境必须使用 MySQL，禁止用 SQLite 本地测试替代 MySQL 并发测试。

# 第一部分：P0 上线阻塞问题

## 3. 客户端 WebSocket 地址不适用于生产

### 问题

本地通常使用 `ws://localhost:8080` 或硬编码内网 IP。生产环境会出现：

- 公网用户无法访问内网地址；
- HTTPS/小游戏环境无法安全连接明文 WebSocket；
- IP 变化需要重新发布客户端；
- 无法统一管理证书、限流和攻击防护；
- 正式域名未加入快手小游戏网络白名单。

### 解决方案

- 准备完成 ICP 备案的正式域名，例如 `wss://game-ws.example.com`；
- 在阿里云 ALB 配置 HTTPS/WSS `443` 监听；
- TLS 在 ALB 终止，ALB 到 ECS 使用私网 `ws://:8080`；
- 生产构建注入 WSS 地址，禁止硬编码 IP；
- 将域名加入快手小游戏域名白名单；
- 增加证书到期告警和续期流程。

### 验收

- 客户端包内不存在生产内网 IP 和明文公网 `ws://`；
- 公网只能通过正式 `wss://` 域名访问；
- 证书链、域名白名单和 ALB Upgrade 透传验证通过。

---

## 4. 缺少可靠的健康检查

### 问题

TCP 端口可连接不代表应用可用，可能出现：

- Node.js 存活但 MySQL 不可用；
- 初始化未完成就接收流量；
- 服务正在退出但仍接收玩家；
- 事件循环严重阻塞但端口探测正常。

### 解决方案

将 WebSocket 挂载到 HTTP Server，提供：

- `/healthz`：进程存活；
- `/readyz`：初始化完成、MySQL 可访问、schema 完整且非 draining；
- `/metrics`：只允许私网访问，暴露连接、房间、事件循环和数据库指标。

ALB 使用 `/readyz` 做健康检查。不可接流量时返回 `503`。

### 验收

- DB 断开时 `/readyz` 返回失败；
- draining 时 `/readyz` 返回 `503`；
- ALB 能自动摘除不健康实例；
- `/healthz` 与 `/readyz` 语义不混用。

---

## 5. 缺少完整优雅关闭

### 问题

生产环境通常通过 Docker、systemd、云助手或编排系统发送 `SIGTERM`。直接终止会造成：

- 新玩家仍进入匹配；
- 牌局和计时器被强制中断；
- 结算事务可能尚未完成；
- 客户端无法获得维护提示；
- 数据库连接不能正常关闭。

### 解决方案

同时处理 `SIGTERM` 和 `SIGINT`，按顺序关闭：

1. 服务进入 draining；
2. `/readyz` 返回 `503`；
3. 停止新连接和新匹配；
4. 保留存量牌局运行；
5. 等待牌局结束或到达最大窗口；
6. 通知剩余客户端维护；
7. 对未完成牌局标记 `aborted` 并补偿；
8. 关闭 WebSocket；
9. 清理所有 timer；
10. 关闭数据库连接；
11. 退出进程。

### 验收

- `SIGTERM` 演练不会产生重复结算；
- draining 后不再创建新匹配；
- 最大退出时间到达后进程可以安全退出；
- 存量连接收到明确关闭原因。

## 6. 当前架构不能直接多实例

### 问题

如果把两台当前版本的 ECS 同时加入 ALB：

- 同账号可能进入两套匹配队列；
- 重连可能落到找不到原房间的实例；
- join ticket 和 reservation 无法跨进程识别；
- 限流状态不一致；
- 房间计时器和机器人调度无法接管；
- 可能出现房间状态分裂和重复操作。

### 一期方案

- 只保留一台活动游戏 ECS；
- 备用 ECS 不接流量或权重为 0；
- ALB 后端同一时刻只能有一台正常权重实例；
- 通过备用镜像、自动部署和人工切换降低恢复时间。

### 二期方案

引入 Tair/Redis，迁移：

- 匹配队列和会话；
- 账号在线路由；
- room 到 shard 的映射；
- join reservation 和 ticket 状态；
- 账号/IP/设备集中限流；
- 分布式锁、租约和 fencing token。

### 验收

在共享状态和分片验收前，禁止双活动实例。粘性会话只能作为路由优化，不能作为一致性基础。

## 7. 服务重启会丢失进行中牌局

### 问题

RDS 保存持久数据，但内存房间、手牌、计时器和连接无法在重启后恢复。故障可能发生在门票扣除、冻结资金或结算前后。

### 一期方案：可补偿但不可恢复

- 每次启动生成新的 `serverGenerationId`；
- 数据库记录比赛所属 generation；
- 启动时识别上一 generation 未完成比赛；
- 标记为 `aborted`；
- 不执行未确认完成的输赢；
- 对门票、冻结和预占做幂等返还；
- 记录补偿流水和中止原因；
- 客户端展示统一故障补偿提示。

### 二期方案：按需恢复

如果业务要求牌局恢复，增加：

- 房间周期快照；
- 关键动作事件序列；
- sequence/generation 校验；
- 计时器剩余时间持久化；
- 房间租约；
- 新实例恢复与客户端状态重放。

### 验收

- 进程在叫地主、出牌和结算前后崩溃，资金都保持一致；
- 补偿可重复执行且不会重复退款；
- 未完成比赛均有最终状态和审计记录。

---

## 8. 禁止 SQLite 路径，统一 MySQL 并发验证

### 问题

SQLite 与 MySQL 的事务、锁和 SQL 语法差异曾导致运行时事故；本项目已约束为 MySQL-only。任何本地 SQLite 测试都会掩盖：

- 并发事务；
- MySQL 死锁和锁等待；
- 连接池耗尽；
- 网络抖动和主备切换；
- SQL 类型、索引和排序规则差异；
- 幂等写入的真实竞态。

### 解决方案

删除 SQLite 路径，建立 MySQL 集成环境并覆盖：

- 并发登录和钱包初始化；
- 同一幂等键并发写入；
- 多玩家同时扣门票；
- 集中结算和重复结算；
- 死锁重试；
- 连接中断与事务回滚；
- RDS 主备切换；
- 慢 SQL 和锁等待。

数据库要求：

- 使用 InnoDB；
- 禁止新增 SQLite 依赖、`.db` 文件、`ON CONFLICT`、`PRAGMA` 或双方言分支；
- 保留 `wallet_ledger.idempotency_key` 唯一约束；
- 对可重试死锁实施有限次数重试；
- 所有外部 I/O 和数据库写操作设置超时；
- 连接池按压测配置，禁止盲目调大。

## 9. 数据库变更流程不完善

### 问题

应用启动只做 schema 检查，生产容易发生：

- 新代码依赖的表还没创建；
- migration 执行中途失败；
- 新旧版本无法同时兼容；
- 回滚后旧代码无法读取新 schema；
- 大表 DDL 阻塞业务。

### 解决方案

采用独立 migration 和 expand/contract：

1. 先增加新表、列和索引；
2. 新旧代码同时兼容；
3. 再发布新代码；
4. 稳定后停止使用旧字段；
5. 后续独立版本再清理旧结构。

migration 要求：

- 发布前执行并审批；
- 执行前创建备份或恢复点；
- 应用运行账号不具备 DDL 权限；
- migration 失败时禁止切流；
- 紧急回滚不删除新增字段和表。

---

## 10. 生产密钥管理风险

### 问题

生产环境可能出现：

- AppSecret 被提交 Git；
- secret 进入镜像层或 CI 日志；
- 多人共享数据库密码；
- 测试和生产共用密钥；
- 身份盐误轮换导致账号映射整体变化。

### 解决方案

使用 KMS Secrets Manager 管理：

- `DDZ_AUTH_SECRET`；
- `DDZ_KWAI_APP_SECRET`；
- RDS 凭据；
- 遥测脱敏密钥。

要求：

- ECS 使用 RAM 实例角色读取指定 secret；
- 镜像不包含真实 `.env`；
- CI 不读取生产运行时 secret；
- 不同环境完全隔离；
- 日志统一过滤密码、token 和 session key；
- 身份盐、认证密钥和埋点脱敏盐分离；
- 快手身份派生盐为代码内置常量，修改它等同全量账号迁移。

# 第二部分：P1 正式放量挑战

## 11. 长连接超时与重连风暴

### 问题

ALB、NAT 和移动网络会中断空闲连接。大量连接同时断开会触发集中重连、认证、钱包查询和匹配恢复，形成瞬时洪峰。

### 解决方案

- ALB 空闲超时设置为 600 秒或按配额调整；
- 客户端每 20～30 秒心跳；
- 服务端 60～90 秒无心跳再判定失联；
- 重连采用指数退避和随机抖动；
- 同账号新连接成功后安全关闭旧连接；
- 登录和钱包同步设置软限流；
- 监控每秒新连接、重连率和认证 QPS。

---

## 12. 快手登录接口成为外部依赖

### 问题

`code2session` 可能超时、限流、返回异常或出现网络故障，大量重连还会放大调用量。

### 解决方案

- 设置 3～5 秒硬超时；
- 只对明确的网络错误做有限重试；
- 优先复用有效 session token；
- 监控成功率、延迟和错误码；
- 对外部接口配置熔断；
- `strict` 模式认证失败不得降级为游客；
- 平台故障时返回明确可重试错误；
- 准备平台接口故障 Runbook。

---

## 13. 进程内限流无法抵御真实攻击

### 问题

攻击者可以创建大量连接、更换 IP 或设备，绕过单连接限流，并通过登录、创建账号、奖励和非法消息消耗 CPU、数据库和日志资源。

### 一期方案

- ALB/WAF 做源 IP 和连接速率防护；
- 限制新账号创建速率；
- 保持消息大小、字段数量和协议白名单；
- 为安全日志设置采样与限速；
- 设置单实例最大连接数；
- 高风险奖励和钱包接口使用更严格业务限额。

### 二期方案

- 使用 Redis/Tair 实现账号、IP、设备维度集中限流；
- 增加黑名单、灰名单和风控事件；
- 统一多实例限额；
- 对奖励、钱包和匹配分别治理。

---

## 14. 生产日志难以检索和关联

### 问题

终端文本日志在生产并发下无法有效关联连接、用户、房间、比赛、事务和版本，而且容易泄漏敏感信息或产生高额费用。

### 解决方案

输出结构化 JSON 日志，至少包含：

- `timestamp`；
- `level`；
- `serverVersion`；
- `serverGenerationId`；
- `requestId`；
- `connectionId`；
- 脱敏 `accountId`；
- `roomId` / `matchId`；
- `eventType`；
- `durationMs`；
- `errorCode`。

日志分类写入 SLS：

- 应用日志；
- 安全日志；
- 业务埋点；
- 结算审计；
- 发布审计；
- ALB 访问日志。

禁止记录 token、session key、openId 明文、secret、数据库密码和其他玩家完整手牌。

## 15. 只监控 CPU 和内存无法反映业务可用性

### 问题

服务可能 CPU 很低但全部登录失败，也可能连接正常但匹配、结算或机器人状态已经卡死。

### 解决方案

建立四层监控：

### 基础设施

- ALB 活跃连接、新建连接、4xx/5xx、后端健康和带宽；
- ECS CPU、内存、磁盘和网络；
- RDS CPU、连接、锁等待、死锁、慢 SQL 和存储。

### Node.js

- Heap 使用率；
- GC 次数与耗时；
- 事件循环延迟；
- 未捕获异常；
- 活跃 handle/timer；
- 进程重启次数。

### 游戏业务

- 在线连接和活跃房间；
- 匹配队列长度与等待 P50/P90/P99；
- 开局、完成、异常中止；
- 结算成功率；
- 重连恢复成功率。

### 资金安全

- 幂等冲突；
- 事务失败；
- 数据库死锁；
- 结算守恒失败；
- 补偿成功率；
- 异常余额，目标为 0。

---

## 16. 埋点上报可能反向影响游戏

### 问题

游戏进程同步调用埋点平台会导致出牌、匹配或结算被上报延迟拖慢；重试还可能占满事件循环或磁盘。

### 解决方案

- 游戏代码只产生本地事件；
- Agent/Collector 异步采集；
- 批量压缩发送；
- 设置超时、指数退避和熔断；
- 使用有界磁盘缓冲；
- 缓冲满时先丢 debug 和低优先级埋点；
- 结算、安全和发布审计优先级最高；
- 一期写 SLS，二期再异步同步 IDC；
- IDC 不可用不得阻塞玩家主链路。

## 17. Node.js 单事件循环容量容易被高估

### 问题

8C16G ECS 不代表单 Node.js 进程可以线性使用 8 核。事件循环、JSON 序列化、房间广播、机器人计算、日志和集中结算都可能成为瓶颈。

### 解决方案

压测必须模拟完整游戏，而不是只建立空连接：

- 登录；
- 钱包同步；
- 匹配和机器人补位；
- 出牌与广播；
- 断线重连；
- 集中结算；
- 非法消息；
- RDS 抖动。

重点观察：

- 单核 CPU；
- 事件循环 P95/P99；
- Heap 和 GC；
- 每秒出站消息和字节；
- RDS 事务和锁等待。

正式稳定承载建议不超过压测极限的 50%～60%。

## 18. 广播放大导致带宽估算失真

### 问题

一条玩家操作可能触发房间状态、三方广播、手牌同步、倒计时和提示，一条上行可能放大成 5～8 条或更多下行消息。

### 解决方案

- 压测统计真实入站和出站字节；
- 合并短时间重复状态广播；
- 避免每次操作发送完整大对象；
- 私有数据只发送给对应玩家；
- 设置连接和房间广播上限；
- 出口带宽保留 1.5～2 倍余量；
- 语音流量单独测算。

---

## 19. 计时器和房间状态可能长期泄漏

### 问题

短时间本地测试不容易发现房间 Map、断线 timer、旧回合 timer、机器人 watchdog、WebSocket 闭包和限流桶的泄漏。

### 解决方案

- 所有房间提供统一 `dispose()`；
- timer 保存引用并集中清理；
- timer 回调检查 room generation 和 sequence；
- 非关键 timer 使用 `unref()`；
- 定期扫描孤儿房间、预约和限流桶；
- 监控房间数、timer 数、Heap、GC 和创建/销毁差值；
- 执行 24～72 小时稳定性压测。

---

## 20. 发布与回滚会中断牌局

### 问题

生产发布时玩家正在游戏，数据库可能已迁移，新旧协议可能不兼容，新版本也可能启动失败。

### 解决方案

- 使用不可变镜像或版本化制品；
- 按 Git commit 和镜像 digest 部署；
- 发布前创建 RDS 恢复点；
- migration 先执行且向后兼容；
- 旧实例进入 draining；
- 超过等待窗口后按统一规则补偿；
- 新版本执行登录、匹配、出牌和结算冒烟；
- 保留上一镜像用于回滚；
- 记录版本、配置、migration、操作者和审批；
- 二期使用备用 ECS 先验证再切换。

---

# 第三部分：P2 长期运营挑战

## 21. RDS 高可用不等于数据绝对安全

### 问题

主备可以处理部分基础设施故障，但不能防止错误 SQL、应用重复扣款、误删、错误 migration 和凭据泄漏。

### 解决方案

- 自动备份和日志备份；
- 正式放量后启用跨地域备份；
- 每季度执行恢复演练；
- migration 前创建恢复点；
- DBA、应用和审计权限分离；
- 高风险 SQL 双人审批；
- 钱包和流水定期自动对账；
- 监控异常余额和结算守恒；
- 用恢复演练记录真实 RTO。

---

## 22. IDC 互通引入新的攻击面

### 问题

两侧网络如果直接打通，可能导致 ECS 横向访问 IDC、IDC 直连生产数据库、CI 持有长期高权限凭据，以及跨边界日志泄漏。

### 解决方案

- 不做扁平网络互通；
- 使用固定 NAT EIP + 七层出口代理；
- 只允许指定 IDC 域名、端口和路径；
- 使用 HTTPS/mTLS；
- CI 使用 OIDC/STS 短期凭据；
- IDC 通过阿里云 API 或云助手发布，不直接 SSH；
- SLS 保持云内主观测；
- IDC 断链时使用有界缓冲和熔断；
- 跨边界字段完成脱敏和安全评审；
- 开启 ActionTrail、VPC Flow Log 和出口审计。

---

## 23. CI/CD 供应链风险

### 问题

自动化可能带来依赖污染、基础镜像漏洞、CI 凭据泄漏、可变标签不可追溯和未审批发布等问题。

### 解决方案

- 固定依赖和基础镜像 digest；
- 生成 SBOM；
- 扫描 npm、系统包和镜像漏洞；
- 未豁免高危漏洞默认阻断；
- 镜像签名和部署前验签；
- 生产按 digest 部署；
- CI、部署和 migration 权限分离；
- 使用短期 STS；
- 生产发布审批；
- ActionTrail 记录云 API；
- 镜像禁止包含 Git、测试数据、AccessKey 和 secret。

---

## 24. 缺少值班和事故处理体系

### 问题

如果没有人员和流程，告警发生后可能没人处理、不知道谁能回滚、多人同时操作，或者无法决定用户补偿。

### 解决方案

上线前明确：

- 业务负责人；
- 技术负责人；
- 云资源管理员；
- DBA；
- 安全负责人；
- 值班联系人；
- 用户补偿审批人。

准备 Runbook：

- 服务无法连接；
- 登录全部失败；
- RDS 不可用；
- 结算或钱包对账异常；
- ECS 故障切换；
- 证书到期；
- DDoS/恶意连接；
- 日志费用异常；
- 应用回滚；
- 未完成牌局补偿。

---

## 25. 生产成本容易失控

### 问题

成本不仅来自 ECS 和 RDS，还包括 ALB LCU、公网出站、SLS、备份、WAF、高防、NAT、跨云流量、备用 ECS 和 Tair/Redis。

### 解决方案

- 设置月度预算和费用告警；
- 监控公网带宽和 ALB LCU；
- 日志分级、采样和生命周期；
- 禁止长期启用 debug 日志；
- 一期真实运行后再调整 ECS/RDS；
- WAF 和高防按活动与风险采购；
- 比较常驻热备和镜像冷备成本；
- 跨 IDC 优先传指标和聚合埋点，不默认传全量日志。

## 30. 最终建议

### 上线前

不要以“本地能跑”和“测试用例通过”替代生产就绪验收。优先补齐：

- 正式网络入口；
- 健康检查；
- 优雅关闭；
- MySQL 并发与迁移；
- 资金补偿；
- 密钥；
- 日志和监控；
- 备份恢复；
- 发布回滚。

### 一期生产形态

> 公网 ALB + 单活动私网 ECS + 跨可用区 RDS MySQL + KMS + SLS + 云监控

该阶段接受进行中牌局不可恢复，但必须保证已提交资金数据正确、异常牌局可识别、相关资产可幂等补偿。

### 二期演进

按以下顺序推进：

1. 活动/备用 ECS 与自动切换；
2. CI/CD、镜像扫描签名和 STS；
3. IDC 安全互通和双通道观测；
4. 容量确有需要后再引入 Tair/Redis；
5. 只有完成共享状态、分片和一致性验收后才允许多活动实例。

生产化不是一次部署动作，而是把代码、基础设施、数据、安全、发布、监控和人员流程组成可持续运行的完整系统。
