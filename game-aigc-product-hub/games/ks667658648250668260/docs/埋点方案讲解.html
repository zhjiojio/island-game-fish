AIGC 小游戏埋点：让 AI 没机会漏埋

核心不是「怎么检查 AI 埋没埋」，而是「让埋点不需要 AI 去埋」 · 2026-09-17

1问题是什么

埋点是 vibe coding 里唯一一类「写错了但永远不会被自然发现」的代码。它没有肉眼可见的功能表现 —— 漏埋、写错、没执行，游戏照样跑得好好的。等两周后看板一片空白，赛马周期已经废了。

AI 说

看不出异常
→

花了钱
→
T+14 看板
数据是空的
→
整个赛马
周期作废

3方案逻辑：埋点是「框架副作用」，不是「业务代码」

让 AI 写业务逻辑时物理上无法绕过埋点。三个收口手法：

❌ 现在：埋点是「额外动作」

// 业务代码里插一句埋点
function enterLevel(lv){
  Analytics.levelStart(lv.idx);  // 靠记得
  render(lv);
}
// AI 复制粘贴时删掉这行 → 静默失效
→

✅ 改造：埋点是「唯一入口的必经之路」

// 埋点在加载器里，业务碰不到
function loadStage(id){
  const st = STAGES[id];       // 数据驱动
  T.stage_enter(derive(st));  // 不可绕过
  return render(st);
}
// AI 想进关卡只能走这里 → 必然有数据
手法做法消灭了什么风险
① 数据驱动埋点 ID 从关卡表/剧本表自动拼，不手写新增关卡/节点忘了埋
② 事件代理Btn.add({id,...}) 注册即埋点，点击由统一分发器上报新增按钮忘了埋
不注册就没按钮，注册就必须给 id
③ SDK 包一层禁止业务直调 createRewardedVideoAd，统一走 AdService.show({slot,from})，6 个生命周期事件自动全发广告漏斗缺环
顺带修复人均触点 0.36 的归因断层
效果：新游戏只要用了脚手架的 loadStage / Btn.add / AdService，四条总线数据自动是全的。埋点从「AI 的自觉」变成「框架的副作用」。

6为什么好 / 代价是什么

✓ 优势

  • 漏埋从概率问题变成结构问题不再依赖 AI 的自觉或人的 review，AI 想进关卡只能走唯一入口
  • AI 越多产越受益新增 100 个节点、10 个关卡，埋点自动跟上，边际成本为 0
  • 跨游戏可比统一 Stage 抽象后，找茬第 7 关和剧情第 23 节点能画在同一张流失曲线上
  • AIGC 归因链完整公共维度自动注入 tplId/themeId/assetBatch，能回答「该押哪个模板/题材」
  • 问题暴露在构建期而不是上线两周后的空看板
  • 已被你们自己验证未婚妻 252 节点漏埋 0，不是理论推演

! 劣势与代价

  • 存量改造有成本老铁 12 处调用点要收口，动的是核心流程，有回归风险 → 新老双发一个版本，数仓校准后再停老的
  • 框架约束降低灵活性AI 想「就这里特殊处理一下」会被 CI 挡住，短期显得别扭 → 留 7090-7099 自定义沙盒段，但数仓不建标准模型
  • Stage 抽象有信息损耗把关卡和剧情节点压成同一模型，会丢玩法特有语义 → 品类层 7060-7079 补细节，标准层只保通用
  • 依赖 DE 排期codegen、Hive 表、看板都不在我们手里 → 先自建通道 B 跑起来，DE 到位后迁移
  • 剧情类 stageSeq 需拓扑排序剧情有分支，线性序号要靠 BFS 生成，改剧本会变号 → 序号一经生成即冻结，新节点追加不重排
  • L0 挡不住「代码写了但分支走不到」静态手段管不了运行时 → 这正是 L3 真机自证要补的
