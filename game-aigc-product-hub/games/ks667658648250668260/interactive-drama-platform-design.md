## 0. 一个必须先说的关键情报

**我们拆的《华君传》，就是规划文档里竞品第 2 位 Yoroll（LinearGame）的旗舰案例**
（文档原文：「《华君传·翻牌吧女帝》：3周 200万抖音小游戏玩家」）。

这意味着这次拆解的性质变了 —— 不是「拆了一款游戏」，而是：

> **我们拿到了头号竞品生产平台的「运行时输出规格」。**
> 他们的编辑器最终导出什么结构的 JSON、数值系统怎么记账、
> 广告门埋在哪一层、QTE 引擎有哪些参数 —— 全部反推出来了。

**竞品编辑器长什么样不重要，重要的是它「吐出来的东西」长什么样。**
我们现在有了这个标准答案，可以直接对着它设计我们的 Runtime Schema，
少走 6~12 个月的格式试错。这是本方案最大的信息优势。

## 1. 核心判断：平台该怎么设计？

### 1.1 三个从拆解里反推出的架构结论

#### 结论一：先定 Runtime Schema，再做编辑器（顺序不能反）

Yoroll 整套产品的地基是这一句：

```
https://lineargame.top/h5/index.html?config=ZH
                                     ^^^^^^^^^
```

**换一个 config 参数 = 换一整款游戏。**
引擎（PixiJS 播放器）零改动，内容全部是外部 JSON + CDN 素材。

这决定了一件事：**平台的真正资产不是编辑器，是那份 Schema 和那个 Runtime。**

- 编辑器是可替换的（今天用 React Flow，明天可以换）
- Schema 和 Runtime 是不可替换的（一旦有 100 个项目在跑，改格式就是灾难）

规划文档 Phase 1 把「互动剧情树可视化编辑器」列为首要交付，
**我建议调整为：Phase 1 的第一交付物是 `ksdrama-schema v1.0` + Runtime 播放器。**
编辑器排第二。理由：Schema 定错，后面全部返工；编辑器丑一点，内部种子用户能忍。

#### 结论二：必须做「双层数据模型」，编辑态 ≠ 运行态

从拆解能清楚看到 Yoroll 的运行态文件极度精简（ch1.json 只有 8.5KB / 17 节点），
里面**没有任何创作过程信息** —— 没有 Prompt、没有分镜说明、没有版本、没有废弃分支。

而 End2X 的 `ScriptDeskProject` 恰恰全是创作过程信息（7 阶段产物、多版本 artifact）。

**这两个是不同的东西，不能混成一个文件。**

```
┌────────────────────────────────────────────────┐
│  编辑态 ProjectDoc（服务端，重，含全过程）        │
│  · 七阶段产物 + 多版本                          │
│  · 每个节点的 Prompt / 分镜 / 素材关联           │
│  · 协作痕迹、评论、废弃分支                      │
│  · 审核状态、合规检测记录                        │
└───────────────────┬────────────────────────────┘
                    │  Compile（编译，单向）
                    ▼
┌────────────────────────────────────────────────┐
│  运行态 RuntimeBundle（CDN，轻，只含可玩内容）   │
│  · game.json + ch{N}.json + i18n.csv           │
│  · 归一化坐标、节点图、广告门、数值效果          │
│  · 目标：单章 < 15KB，首屏预热可控              │
└────────────────────────────────────────────────┘
```

**「编译」这个动作是平台的核心技术资产**，它负责：
死链检测、孤儿节点清理、广告门配额校验、素材 CDN 化、
文案抽成 i18n 表、结局可达性验证、包体积预算检查。

这一步做扎实，等于把「上架前才发现剧情走不通」的问题提前到编辑期解决。
（我本地已有 `story-graph-orphan-audit` skill 做过这类 BFS 可达性审计，可直接复用为编译器的校验模块。）

#### 结论三：把「变现」下沉成 Schema 的一等公民，而不是编辑器上层的配置面板

规划文档把「IAA 变现配置」列为第 5 个功能模块（并列关系）。
但从拆解看，Yoroll 的广告是**编织进内容结构里的**：

```json
// 章节级
{ "id":"5", "title":"北境秋狩", "unlockAdsRequired": 2 }

// 节点级（游戏状态机里有 chapterAdPending 字段）
// 内容级（宣舞 8 免费 / 8 广告解锁，编号交错分布）
```

广告不是「配在旁边」，是「长在节点上」。

所以 Schema 里必须原生定义广告位类型，编辑器只是它的可视化：

```typescript
type AdGate =
  | { kind: 'chapter_unlock';  count: number }        // 章节门
  | { kind: 'choice_unlock';   choiceIndex: number }  // 选项门（第4选项）
  | { kind: 'ending_unlock';   endingId: string }     // 结局门
  | { kind: 'content_unlock';  assetId: string }      // 内容门（如舞蹈）
  | { kind: 'revive';          nodeId: string }       // 复活门（死亡后）
```

**注意最后一个 `revive`（复活门）—— 这是 Yoroll 漏掉的钱。**
它有 12 个即死结局，但玩家死了只能回溯重看，没有「看广告原地复活」。
这是一个现成的增量广告位，而且情绪时机极好（刚死，最不甘心）。

### 1.2 平台分层架构

```
┌──────────────────────────────────────────────────────────┐
│  L5  数据与增长层                                          │
│  数据看板 / 广告门 A/B / 卡点热力图 / 分支流向桑基图        │
├──────────────────────────────────────────────────────────┤
│  L4  发行层                                                │
│  一键打包 / 分包策略 / 快手开放平台提交 / 合规预检          │
├──────────────────────────────────────────────────────────┤
│  L3  编辑层（可替换）                                       │
│  剧本台(7阶段) / 剧情树画布 / 时间线QTE编辑 / 素材中心      │
├──────────────────────────────────────────────────────────┤
│  L2  生成层                                                │
│  LLM剧本 / 分镜 / Kling视频 / 角色一致性 / TTS / BGM        │
├──────────────────────────────────────────────────────────┤
│  L1  ★ 核心资产层（不可替换）                               │
│  ksdrama-schema  +  编译器(Compiler)  +  Runtime播放器      │
└──────────────────────────────────────────────────────────┘
```

**投入优先级：L1 > L4 > L3 > L2 > L5**

L2（AI 生成）反而不该自研 —— 接 Kling / 内部模型即可，这是别人的战场。
L4（发行）优先级要高于 L3（编辑器），因为**「能上架」是唯一的不可替代价值**，
而编辑器体验差可以靠模板和人工弥补。

### 1.3 Schema 设计草案（`ksdrama-schema v1.0`）

直接吸收拆解成果，逐条说明「为什么这么设计」：

```typescript
interface RuntimeBundle {
  meta: {
    gameId: string;
    title: string;
    cdnBase: string;
    orientation: 'portrait' | 'landscape';   // ★ 快手必须默认 portrait
    schemaVersion: '1.0';
  };

  chapters: Chapter[];
  statConfigs: StatConfig[];
  characterConfigs: CharacterConfig[];
  adPolicy: AdPolicy;        // ★ 新增：全局广告策略（Yoroll 没有）
  compliance: Compliance;    // ★ 新增：合规元信息（Yoroll 没有）
}

interface Chapter {
  id: string;
  title: string;             // i18n key
  dataPath: string;          // ch{N}.json
  coverImage: string;
  finishImage: string;
  unlockAdsRequired: number; // ← 直接沿用 Yoroll 设计
  startNodeId: string;
}

interface Node {
  id: string;
  title: string;
  video: string;
  thumbnail?: string;

  // —— 分支 ——
  question?: string;
  choices?: Choice[];
  next?: string;
  autoSelectByCondition?: boolean;   // ← 关键：条件自动选路

  // —— 限时选择 ——
  duration?: number;
  defaultChoiceIndex?: number;

  // —— 玩法 ——
  interaction?: Interaction;         // ← 即 QTE，改名更准确

  // —— 数值 ——
  statEffects?: Record<string, {value:number}>;
  characterEffects?: Record<string, Record<string,{value:number}>>;

  // —— 结局 ——
  isEnd?: boolean;
  endType?: 'death' | 'chapter' | 'game';
  endDesc?: string;
  endBgUrl?: string;

  // —— ★ 我们新增 ——
  adGate?: AdGate;                   // 节点级广告门
  reviveEnabled?: boolean;           // 死亡节点是否可看广告复活
  hookLevel?: 0|1|2|3;               // 情绪钩子强度（供数据分析与排期）
}

interface Choice {
  label: string;
  next: string;
  conditions?: Condition[];
  immediateSettle?: boolean;
  adGate?: AdGate;                   // ★ 第4选项 = 广告解锁选项
}

// 条件系统（Yoroll 用魔数 1003，我们改成可读枚举）
type Condition =
  | { type: 'stat_gte';       stat: string; value: number }
  | { type: 'char_favor_gte'; char: string; value: number }
  | { type: 'char_favor_gt_other'; char: string; other: string }  // ← 原 1003
  | { type: 'flag';           flag: string }
  | { type: 'visited';        nodeId: string };
```

**Interaction（玩法）—— 这是我们要重点超越的地方：**

```typescript
interface Interaction {
  type: InteractionType;
  triggerAtSecond: number;      // ★ 挂在视频时间轴上，不是独立关卡
  duration: number;
  area?: { x:number; y:number; w:number; h:number };  // 归一化 0~1
  resultMap: { success: string; fail: string };        // ★ 成败分流
  instruction?: string;
  config: Record<string, unknown>;
}

type InteractionType =
  // 通用原子玩法（引擎内置，任何题材可用）
  | 'tap'          // 连点
  | 'longpress'    // 长按
  | 'swipe'        // 滑动/擦除
  | 'hotspot'      // 场景点击探索
  | 'trace'        // 描摹（剪纸/画符/写字）
  | 'jigsaw'       // 拼图
  | 'fill_blank'   // 填空（拟诏/写信/填药方）
  | 'pick_option'  // 图形化选择（面具/服饰/礼物）
  | 'timed_choice' // 限时选择
  // 快手特化（后续）
  | 'shake' | 'voice';
```

**关键设计：把 Yoroll 的 9 种具体玩法抽象成 9 个「通用原子」。**

Yoroll 的 `imperial_seal`（拟诏盖印）、`lantern_release`（放河灯）、
`paper_cutting`（剪纸）、`mask_choice`（傩戏面具）是**硬编码在引擎里的古风专属玩法**。
换个现代题材就全废了。

我们改成：
| Yoroll 硬编码 | 我们的通用原子 | 换皮后可以是 |
|---|---|---|
| imperial_seal 拟诏 | `fill_blank` | 填诏书 / 写情书 / 填合同 / 开药方 |
| lantern_release 河灯 | `pick_option`(带score) | 放河灯 / 选礼物 / 挑戒指 |
| paper_cutting 剪纸 | `trace` | 剪纸 / 画符 / 描红 / 签名 |
| mask_choice 面具 | `pick_option`(带video) | 面具 / 战袍 / 造型 / 武器 |

**同样 9 种玩法，我们的可复用性是它的 N 倍。**
创作者只需配 JSON（换图、换文案、换视频），不需要工程介入。
这直接对应规划文档里「用户教育成本高」的风险 —— 原子化的玩法更容易做成模板。

**合规块（Yoroll 完全没有，是我们的强制差异化）：**

```typescript
interface Compliance {
  aiGeneratedRatio: number;        // AI 生成占比
  aiLabelRequired: boolean;        // >30% 自动置 true
  aiLabelText: string;             // 展示文案
  promptArchiveId: string;         // ★ Prompt 存档 ID（政策要求留存）
  licenseDocs: string[];           // 授权合同
  filingType: 'platform' | 'provincial' | 'national';  // 备案层级
  contentScanReport: string;       // 内容检测报告 ID
}
```

规划文档第四节写得很清楚：
「2026年7月三部 AI 互动短剧因未标注 AI + 无完整备案被全网下架」。

**这条如果只靠人工自觉，早晚出事。必须做成 Schema 强制字段 + 编译期硬校验：**
`aiGeneratedRatio > 0.3 且 aiLabelRequired = false` → **编译失败，不允许出包。**

### 1.4 从拆解里提炼的「叙事设计规范」（内置成模板约束）

这部分是**内容侧的方法论沉淀**，应该固化进平台的模板和校验器，
让新手创作者「不懂设计也能做出及格线以上的东西」。

| 规范 | 来自拆解的依据 | 平台如何落地 |
|---|---|---|
| **明暗双数值** | favor `showToast:false`（暗涨制造焦虑）／ suspect `showToast:true`（明涨制造紧张） | 新建项目默认给「好感(暗) + 危险(明)」双数值模板 |
| **即死结局当内容放大器** | 18 个结局里 12 个是 death；第3章 15 节点塞 5 个即死 | 校验器提示：death 占比建议 50~65%，过低提示「重玩动机不足」 |
| **菱形收束拓扑** | 分叉→演出→合流→再分叉，终章 4 结局共用 `cab.mp4` 过渡 | 编辑器提供「菱形分支」一键模板；素材复用率纳入成本看板 |
| **终局按累积数值自动判定** | `condition_type:1003` 比较双男主好感 + `auto_select_by_condition` | Schema 原生支持；模板内置「双主角争夺」结构 |
| **数值阶梯 20/50/80** | 单次 +2~+4，需 20~30 次正确互动才满级 | 校验器算「理论满级所需节点数」，超出章节容量则警告 |
| **广告梯度递增** | 章节广告 0→1→1→1→2→2，首章白嫖 | 编译器强制：第 1 章 `unlockAdsRequired` 必须为 0 |
| **变现文案叙事化** | 「5秒」→「五息」；「解锁」→「收入陛下的舞册」 | 提供文案改写模板库，AI 辅助润色广告文案 |
| **双主角互补原型** | 明攻(华君) vs 暗攻(甄桓)，最小角色数吃最大受众 | 角色模板库内置 8 组互补原型对 |

### 1.5 差异化：三个 Yoroll 没做、我们必须做的

规划文档第六节已列了与 End2X 的差异。这里补充**与真正的头号对手 Yoroll 的差异**：

#### 差异一：竖屏优先（Yoroll 是横屏，这是它的原罪）

拆解证据：`screenOrientation: "Landscape"`，渲染 1920×902。

Yoroll 是从 Steam / PC 互动电影思路迁移来的，横屏基因。
但**快手是竖屏产品，老铁是竖着刷的**。横屏 = 每次都要转屏 = 巨大流失。

我们必须 **portrait-first**：
- 默认竖屏 9:16，视频素材生产规范就按竖屏来
- 交互热区适配单手拇指区（屏幕下半部）
- 横屏只作为可选（如舞蹈/大场面才临时转横）

这一条看起来简单，但它决定了**素材生产规范、AI 出图比例、UI 布局**全链路，
必须在 Phase 1 就锁死，后期改不动。

#### 差异二：接快手直播/短剧生态（Yoroll 永远做不到）

规划文档已点出最大机会点：
「快手短剧生态（创作者、IP、用户）是天然供给侧」。

具体可做的连接：
- **短剧 IP → 互动影游**：已有短剧素材直接复用为节点视频，边际成本极低
- **主播 → 角色**：直播主播的形象/声音授权为游戏角色（我本地已有
  `minimax-voice-clone`、`aigc-character-video-pipeline` 两条现成管线）
- **直播间投放**：主播在直播间玩自己的互动影游，观众看广告解锁分支
- **短视频切片分发**：把游戏里的高光分支剪成短视频引流回游戏

这是 Yoroll 在抖音做不到的（它没有生态位），也是快手真正的护城河。

#### 差异三：把「隐藏中台」一次做对

拆解发现 Yoroll 已实现但未开放的一整套系统：

```
虚拟币(getCoins/spendCoins/canAfford) · 签到(claimCheckin/claimDailyLogin)
任务(getChronicleTasks/claimChronicleTask) · 红点(hasPendingRewardDot)
心愿墙UGC(submitWish/likeWish) · AI生图(generatePortrait) · 限时解锁(getUnlockExpiresAt)
```

**这是竞品的路线图，被我们提前看到了。**

其中最值得抄的是 **虚拟币经济**：
- 现状（Yoroll 上线版）：一舞一广告，广告价值不流转
- 隐藏版：看广告 → 赚币 → 币解锁任意内容
- 后者能让玩家为了「攒币解锁那支想看的舞」而**主动多看广告**，
  且币可以用签到/任务发放，直接拉日活

建议：**Runtime 从 v1.0 就预留 wallet 接口**（哪怕先不开放 UI），
避免以后加币系统要改存档结构。

### 1.6 修正后的路线图

对规划文档 Phase 1~3 做三处调整（其余保持）：

| | 规划文档原方案 | 建议调整 | 理由 |
|---|---|---|---|
| **Phase 1 首要交付** | 互动剧情树可视化编辑器 | **改为 Schema v1.0 + Runtime + 编译器** | Schema 定错则全线返工；编辑器可后补 |
| **Phase 1 增补** | — | **portrait-first 素材规范 + 合规硬校验** | 竖屏和合规都是「后期改不动」的地基项 |
| **Phase 2 增补** | — | **复活广告门 + 虚拟币接口预留** | 现成增量广告位；避免存档结构二次迁移 |

**Phase 1 修正后的验收标准（建议写死）：**

> 一个内部团队，用平台在 **10 个工作日内**，
> 把 1 个已有短剧 IP 做成 1 集互动影游（≥15 节点 / ≥2 玩法 / ≥3 结局 / ≥2 广告门），
> 竖屏、通过合规预检、成功上架快手小游戏并跑出真实广告收入。

跑通这一条，比做出 20 个功能模块更有意义。

## 2. 从剧本到上线：全流程 SOP

这套流程融合了：End2X 七阶段方法论 + 我本地已验证的 AIGC 管线 + 快手上架实操经验。

### 2.0 全景

```
S0 选题立项 ──▶ S1 剧本工坊 ──▶ S2 结构设计 ──▶ S3 分镜脚本
                                                      │
                                                      ▼
S7 上架发行 ◀── S6 集成调优 ◀── S5 素材生产 ◀── S4 资产规划
     │
     ▼
S8 数据迭代 ──▶（回流 S0）
```

**关键原则：S2（结构）必须早于 S5（素材生产）。**
Yoroll 的菱形收束和素材复用之所以成立，是因为先定了拓扑再拍片。
反过来做（先拍素材再拼结构）会产生大量废片，成本失控。

### S0｜选题立项（0.5 天）

**做什么**
1. 确定题材 + 主角原型对（从模板库选，如「明攻 vs 暗攻」）
2. 确定规格档位
3. 算成本账，PM 签字

**规格档位建议（Phase 1 只做「中档」）**

| 档位 | 节点数 | 结局数 | 玩法数 | 视频时长 | 广告门 | 预估周期 |
|---|---|---|---|---|---|---|
| 轻 | 15~25 | 3~5 | 2~3 | 8~12 min | 3~5 | 5 天 |
| **中** | **40~60** | **8~14** | **5~8** | **25~40 min** | **6~10** | **10 天** |
| 重 | 90~120 | 14~18 | 10~14 | 60~90 min | 12~18 | 25 天 |

（对标：《华君传》98 节点 / 18 结局 / 14 玩法 / 7 章节门 = 「重」档）

**产出**：`project.yaml`（题材、原型对、档位、成本预算、排期）

**卡点**：成本超预算 / 题材撞合规红线 → 打回

### S1｜剧本工坊（1.5 天）

采用 End2X 七阶段的**前三阶段**，但做了两处改造：

| 阶段 | 输入 | 产出 | 我们的改造 |
|---|---|---|---|
| **1.1 原文索引** | 短剧原片 / 小说 / 一句话创意 | 事实·事件·人物·伏笔索引 | ★ 新增「**素材可复用性标注**」：标出哪些原片镜头可直接复用 |
| **1.2 风格定锚** | 索引 | 叙事口吻、节奏、情绪曲线、创作禁区 | ★ 新增「**快手老铁语感校准**」：禁文艺化表达，名词要一眼看懂 |
| **1.3 留存变现架构** | 索引+风格 | 前30秒钩子、广告门位置、集末峰值 | ★ 新增「**首章零广告**」硬约束 |

**1.2 的老铁语感校准（重要，来自我们已验证的经验）**

这一条是快手特化，必须写进 Agent 指令：

- 名词要农村/下沉市场一秒看懂：用「针线、土炕、油灯、灶膛」，不用「艾叶、水袖」
- 动作要能立刻想象出画面，不要抽象心理描写
- 反面示例：「灯下·婉儿我在」→ 正面：「他说：你不用一个人撑着，我在」

**1.3 的钩子设计（来自拆解 + 规划文档 03 号 Agent）**

- **前 30 秒必须出冲突**（不是铺垫世界观）
- 广告门位置公式：`情绪峰值点 + 1 个节点`（刚被吊起胃口时最愿意看广告）
- 首章 `unlockAdsRequired = 0`（编译器强制）

**产出**：`01-index.md` / `02-style.md` / `03-retention.md`

**卡点**：合规预检（AI 扫红线：低俗复仇 / 畸形婚恋 / 魔改经典 / 亵渎英烈）

### S2｜结构设计（2 天）★ 最关键的一步

对应 End2X 阶段 4~5，是整个流程的**成本控制阀门**。

#### 2.1 分支拓扑设计

**强制采用菱形收束**：

```
        ┌─── B1 ───┐
  A ────┤          ├──── D ────┬─── E1 ───┐
        └─── B2 ───┘           └─── E2 ───┴──── F(合流) ──▶ 结局分岔
```

**路径预算（直接影响成本，必须算）**

```
总节点数 = 主干节点 + Σ(每个分叉的独占节点)
素材复用率 = 1 - (独占节点数 / 总节点数)
目标：素材复用率 ≥ 40%
```

对标《华君传》：终章 4 个结局前共用同一过渡节点、且该视频复用 4 次，
是把复用率拉到极致的做法。

#### 2.2 结局矩阵设计

按拆解验证过的三层结构配比：

| 类型 | 占比 | 数量(中档) | 作用 |
|---|---|---|---|
| `death` 即死 | 55~65% | 6~8 | 制造重玩动机，放大内容消耗 |
| `chapter` 章节通关 | ~25% | 3~4 | 正常推进 + 触发广告门 |
| `game` 真结局 | 15~20% | 2~4 | 最终收束（双主角 × HE/BE） |

#### 2.3 数值系统设计

```yaml
stats:
  - id: favor      # 暗数值
    perCharacter: true
    showToast: false          # ★ 不提示，制造不确定性
  - id: suspect    # 明数值
    perCharacter: false
    showToast: true           # ★ 提示，制造紧张

发放规则:
  普通讨好: +2
  关键/独占选择: +4
  终章排他选择: +8
关系阶梯: 20 / 50 / 80
校验: 理论满级所需正确互动次数 ≤ 本剧总分支点数 × 0.7
```

#### 2.4 终局判定设计

```json
{
  "autoSelectByCondition": true,
  "choices": [
    { "label":"救A", "conditions":[{"type":"char_favor_gt_other","char":"A","other":"B"}] },
    { "label":"救B", "conditions":[{"type":"char_favor_gt_other","char":"B","other":"A"}] }
  ]
}
```

**产出**：`04-topology.json`（节点图骨架，无素材）/ `05-system.json`（数值与结局）

**卡点（自动校验，不通过不许进 S3）**
- ✅ BFS 可达性：无孤儿节点、无死胡同、choices 无悬空引用
- ✅ 所有结局可达，且至少一条路径能走到每个 `game` 结局
- ✅ 素材复用率 ≥ 40%
- ✅ 广告门数量在档位区间内，首章为 0
- ✅ 数值满级可达性

> 这一步的校验器可直接复用我本地的 `story-graph-orphan-audit` skill。

### S3｜分镜脚本（1.5 天）

对应 End2X 阶段 6。**逐节点产出，但要先做资产规划（见 S4）再开拍。**

每个节点产出：

```json
{
  "nodeId": "n_012",
  "shots": [
    { "shotId":"s1", "desc":"...", "duration":6,
      "camera":"中景推近", "characters":["A"],
      "videoPrompt":"...", "firstFramePrompt":"...",
      "dialogue":"...", "voiceRole":"A", "sfx":"...", "bgm":"tense" }
  ],
  "interaction": {
    "type": "swipe",
    "triggerAtSecond": 8.1,     // ★ 必须标注在视频第几秒触发
    "resultMap": { "success":"n_013", "fail":"n_099_death" }
  }
}
```

**玩法设计规范（从拆解提炼，写进 Agent 指令）**
1. 玩法必须**挂在视频时间轴上**（`triggerAtSecond`），不做独立关卡
2. 玩法必须**能导致死亡**（`resultMap.fail` 指向 death 节点），否则玩家不认真
3. 热区用**归一化坐标**，且竖屏下必须落在拇指可达区
4. 每 3~5 个节点至少 1 个玩法，避免变成纯看片

**产出**：`06-storyboard/{nodeId}.json`

### S4｜资产规划（0.5 天）★ 省钱的关键

**先做资产台账，再开拍。** 这一步能砍掉 30~50% 的生成成本。

```
1. 汇总所有 shots → 去重 → 得到「唯一素材清单」
2. 标注复用关系：哪些节点共用同一段视频（如过渡镜头）
3. 标注来源：
   - [复用] 短剧原片可直接裁切  ← 成本 ≈ 0，快手生态最大优势
   - [生成] 需 AI 生成
   - [改造] 原片 + AI 局部重绘
4. 角色一致性规划：确定参考图 / LoRA 绑定
5. 输出成本预估表
```

**产出**：`asset-manifest.csv`（素材ID / 类型 / 来源 / 复用节点数 / 预估成本）

**卡点**：成本超 S0 预算 → 回 S2 精简拓扑（**不是砍质量，是砍分支**）

### S5｜素材生产（3 天，可并行）

四条流水线并行：

#### ① 视频线
```
首帧图（gpt-image / 内部模型）→ 图生视频（Kling）→ 压缩 → CDN
```
**已知坑（来自实践积累）**
- Kling 有并发限制，需渐进重试
- 敏感内容会被 `safety_violations` 拒绝，需 prompt 改写重试
- 女性角色 prompt 需走合规改写（三层遮盖原则）
- 视频必须 **H.264**，H.265/HEVC 在快手小游戏容器里黑屏

#### ② 语音线
```
音色克隆（minimax voice_clone）→ 批量 TTS（t2a_v2）→ 对齐字幕
```
- 主播授权音色是快手独有优势
- 需注意 RPM 限流

#### ③ 音乐线
```
BGM（minimax music-1.5）—— 游戏 BGM 必须加 --instrumental
```
**铁律**：不加 `--instrumental` 会生成带人声演唱的曲子，会盖过旁白，且能听出是 AI 胡编的词。

#### ④ 图片线
```
封面 / 章节图 / 结局图 / 角色立绘 / 玩法背景图
→ pngquant 压缩 → CDN
```

**统一 CDN 规范**
- 上传后**必须验证 URL 真实可访问**（曾出现「上传假成功」）
- **禁止同名覆盖**（CDN 一年缓存，改了不生效）→ 用 `.v2` 后缀
- 跨 AppID 桶有鉴权绑定，迁移时必须全量校验

**产出**：CDN 素材库 + `asset-manifest.json`（含真实 URL）

### S6｜集成调优（1.5 天）

```
1. 编辑器导入 04/05/06 产物 → 生成 ProjectDoc
2. 素材绑定（自动匹配 assetId）
3. 玩法调参：triggerAtSecond 对齐、热区位置、难度
4. 广告门落位 + 文案叙事化改写
5. 编译 → RuntimeBundle
6. 全路径自动巡演（脚本遍历所有分支，验证无断链、无404）
7. 真机预览（扫码）
```

**编译器强制校验（红线，不通过不出包）**

| 校验项 | 规则 |
|---|---|
| 图完整性 | 无孤儿 / 无死胡同 / 无悬空引用 |
| 结局可达 | 每个 `game` 结局至少一条路径可达 |
| 素材可访问 | 所有 CDN URL 返回 200 |
| 视频编码 | 必须 H.264 |
| 包体积 | 主包 < 平台上限，超出自动分包 |
| 广告门 | 首章为 0；总数在档位区间 |
| **合规** | **AI占比>30% 必须有标识，否则编译失败** |
| 竖屏 | orientation = portrait（除非显式豁免） |

**产出**：`RuntimeBundle` + 快手小游戏工程包 + 预览二维码

### S7｜上架发行（1 天）

```
1. 商店素材：icon(多尺寸) / 分享图 / 加载图
   ★ 注意生图网关不支持 3:2，会静默 fallback 成竖图导致切头，横图用 16:9
2. 合规材料：AI标识 / Prompt存档 / 授权合同 / 备案（按层级）
3. 上传快手开放平台 → 提审
   ★ 上传后必须去后台确认版本号真的更新了（曾出现「上传假成功」）
4. 灰度 → 全量
```

**上架前 10 项自检清单**
1. 版本号三件套已更新
2. 真机首屏无黑屏（清缓存后测）
3. 分包加载正常
4. 所有视频可播（H.264）
5. 广告 SDK 回调正常，看完能真解锁
6. 存档读写正常，杀进程后进度不丢
7. 所有结局实际可达（脚本巡演通过）
8. AI 标识已展示
9. 竖屏显示正常，热区在拇指区
10. 埋点上报正常

### S8｜数据迭代（持续）

**必看的 5 张表**

| 看板 | 关键指标 | 触发动作 |
|---|---|---|
| 漏斗 | 首屏→首选择→首章完成→通关 | 首屏流失>40% → 重做前30秒钩子 |
| 分支桑基图 | 每个选择点的分流比 | 某选项<5% → 文案没吸引力，重写 |
| 卡点热力图 | 各节点退出率 | 退出率突高 → 该节点视频太长/太闷 |
| 广告 | 各广告门曝光/完成/放弃率 | 放弃率>50% → 位置不对，前移或后移 |
| 结局收集 | 各结局到达人数 | 某结局<1% → 路径太隐蔽，加引导 |

**A/B 实验方向**：广告门位置、死亡结局密度、玩法难度、首章长度

## 3. 落地建议：先做什么

如果只能选三件事启动：

**第一件：定 Schema v1.0（1 周）**
直接以本次拆解的结构为蓝本，补上 `adGate` / `compliance` / 通用玩法原子 / portrait。
这是所有后续工作的地基，**必须一次定对**。

**第二件：做编译器 + Runtime（3 周）**
编译器 = 校验 + 打包 + CDN 化；Runtime = 竖屏播放器。
做完这两个，**哪怕编辑器还是手写 JSON，也能出货了**。

**第三件：跑通 1 个真实项目（2 周）**
挑一个已有短剧 IP，走完 S0~S7，真上架、真跑广告收入。
**这个项目的价值不在于赚多少钱，在于它会暴露 Schema 的所有设计缺陷** ——
而这时候改还来得及。
