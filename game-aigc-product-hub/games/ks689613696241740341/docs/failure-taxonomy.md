# 拼豆 · 失败归因清单（Failure Taxonomy）

> 移植来源：GameXpert-Bench GameGen 赛道的 **"Implemented ≠ Functional"** 发现。
> 该研究在 43081 个跨模型运行时事件里做事后池化，得出失败分布：
> **56% 加载/崩溃 · 16% 状态机转移 · 13% 反馈缺失 · 12% 视觉渲染**。
>
> 核心结论：**代码写完了 ≠ 功能可用**。只有 5.32% 的运行时事件符合预期。
> 所以排障必须**按概率降序**走，不能按"哪里看起来可疑"走 —— 后者是直觉，
> 直觉在长尾分布面前系统性失效。

---

## 0. 使用方式（铁律）

任何人报"拼豆有问题 / 打不开 / 玩不下去 / 感觉不对"，**一律从 T1 开始按顺序排**。
禁止跳级。跳级的代价：在 T4 视觉层耗半天，最后发现是 T1 的分包没加载。

每一级都必须给出**可准入证据**（见 `tools/bench/evidence.js`）：
注释、"我看了一下应该没问题"、"逻辑上不会"，一概不算。

---

## T1 · 加载 / 崩溃（先验概率最高 ≈56%）

**为什么排第一**：它的症状最不 specific（黑屏、卡进度、闪退），
所以最容易被误判成"随便什么问题"，同时它又最高频。先排它期望收益最大。

拼豆已知的 T1 触发点：

| 现象 | 根因 | 判据 |
|---|---|---|
| 首屏黑屏 / loading 卡住 | 分包未加载完就 draw | 看 `loadSubpackage` 回调是否真的执行 |
| 清缓存后必黑屏 | 关键素材没进 CRITICAL_ASSETS | 冷启动实测，不看热启动 |
| 主包过大导致加载慢 | 素材没走 CDN / 未 pngquant | `du -sh package/` |
| 语法错误直接白屏 | ES6 语法漏进 ES5 工程 | `node -c package/js/*.js` |

**排查命令**：
```bash
for f in package/js/*.js; do node -c "$f" || echo "语法错误: $f"; done
du -sh package/
```

---

## T2 · 状态机转移（≈16%）

**为什么排第二**：症状看起来像"玩法设计问题"，最容易被错误归类为策划问题，
从而被搁置。但它其实是纯 bug，且**拼豆的核心风险全在这一层**。

拼豆的状态机 = 车位状态 × 队列状态 × 豆阵状态。它的坏味道：

| 现象 | 根因 | 判据脚本 |
|---|---|---|
| 车位占死走不动 | 僵尸车堆积 / ghost 占位 | `PD.simulateRuntime` 返回 `ok:false` |
| 打完第三关又回第一关 | 关卡进度状态未持久化 | 云存档读写日志 |
| 车明明满了却不走 | 离场条件判定分裂 | `parity-audit.js` R3 |
| 求解器说能过但真机过不了 | **口径分裂**（已知坑 10） | `parity-audit.js` L3 |

⚠️ **最贵的一条**：口径分裂不会报错、不会崩溃，只会让红线变成假绿灯。
它是**唯一一类"审计通过反而更危险"的缺陷**，因为它消灭了怀疑。

**排查命令**：
```bash
node tools/bench/parity-audit.js 30 3   # 口径蕴含 + 重复实现探测
node tools/validate-levels.js 30 3      # 8 条红线
```

---

## T3 · 反馈缺失（≈13%）

**为什么排第三**：它不影响"能不能玩"，只影响"玩起来对不对"。
但它对留存的杀伤力被严重低估 —— 玩家不会说"缺少反馈"，
他们只会说"没意思"然后卸载。

拼豆的反馈层清单：

| 事件 | 必须有的反馈 | 已知坑 |
|---|---|---|
| 豆子上车 | 音效 + 震动 + 位移动画 | 震动不能滥用（每颗豆都震 = 手麻） |
| 车装满离场 | 离场动画 + 音效 | — |
| 通关 | `sfxSuccess()` **先**，`playVoice()` **后** | 音效必须在语音前，否则被语音盖住 |
| 车位快满 | 视觉预警 | 缺失 → 玩家不知道自己在走向死局 |
| 三星达成 | 星级动画区分度 | 「三星永远3星」= 阈值用了 minMoves |

---

## T4 · 视觉 / 渲染（≈12%）

**为什么排最后**：它最显眼，所以最容易被最先报告 —— 这正是要压到最后的原因。
显眼 ≠ 高频，显眼 ≠ 高危。先修显眼的 = 用最贵的时间买最便宜的收益。

| 现象 | 根因 |
|---|---|
| 豆阵越界 / 压到行车道 | cell 计算与 `pd-game` 公式不一致（V6） |
| 前期黑色豆看不清 | `COLOR_ORDER` 让黑色过早入场 |
| 立绘铺不满 | `PORTRAIT` 锚点未对齐裙摆 |
| 视频/立绘被 canvas 盖住 | `drawBg` 覆盖了 native 层 |

## 附：归因分布 vs 拼豆实际投入（自查用）

事后复盘时填这张表，如果**投入分布和概率分布严重背离**，说明排障顺序错了：

| 层级 | 先验概率 | 本次实际耗时占比 | 背离？ |
|---|---|---|---|
| T1 加载/崩溃 | 56% | | |
| T2 状态机 | 16% | | |
| T3 反馈 | 13% | | |
| T4 渲染 | 12% | | |

> 注：56% 这个数来自 GameXpert-Bench 的跨模型池化，是**通用游戏开发**的分布。
> 拼豆作为**已上线的成熟工程**，T1 的实际占比应低于 56%、T2 应高于 16%
> —— 因为加载问题在早期就被清掉了，而状态机复杂度是随关卡数持续增长的。
> **这张表的价值不在于绝对数字，而在于强制你先证伪高频项再去查低频项。**
