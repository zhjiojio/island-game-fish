# 拼豆 Bench —— GameXpert-Bench 方法论落地

> 来源：GameXpert-Bench（arXiv 2608.21833）／GameGen ／GameFix
> 落地日期：2026-08-31
> 一条命令：`node tools/bench/bench-all.js 20 3`

---

## 一、为什么要做这件事

原来的验收方式是「跑 `validate-levels.js`，8 条红线全绿就 build」。

这套方式有一个致命的结构性缺陷：**它只能证明当前状态好，不能证明它有能力发现问题**。

一个内容只有 `process.exit(0)` 的空脚本，也能做到 8/8 全绿。

历史事故印证了这一点 —— 已知坑 10：求解器 8 条红线全绿，真机 200 局里 112 局死局。
红线在自己骗自己，而没有任何机制能发现这件事。

GameXpert-Bench 解决的正是同一个问题，只是它面对的是"如何评估模型做游戏的能力"。
它的三个核心设计可以直接搬过来。

## 二、方法论映射表

| GameXpert-Bench 的做法 | 它解决什么 | 拼豆落地 | 脚本 |
|---|---|---|---|
| 证据准入规则 | 防止"声称做了"当成"做到了" | 4 类伪证识别 + 契约符号可达性 | `evidence.js` |
| Implemented ≠ Functional 归因 | 按先验概率排查而非随机猜 | T1/T2/T3/T4 四层分诊表 | `docs/failure-taxonomy.md` |
| 可逆变异 → 零标注真值 | 用变异体杀灭率量化红线能力 | 15 个算子 M01~M15 | `mutators.js` + `gate-audit.js` |
| F2P / P2P 双闸门 | 同时防"假绿灯"和"假红灯" | 基线必须绿 + 缺陷必须被抓 | `gate-audit.js` |
| Strict（高标准带均值） | 平均值掩盖分布，断崖藏在形状里 | S(τ) 生存曲线 + τ∈[90,100] | `strict-curve.js` |
| Explicit → Self-Discovery 落差 | 量化"自主发现能力" | Cliff = 老手胜率 − 随手胜率 | `strict-curve.js` |
| Shared Rubric 事后池化 | rubric 反映现实而非想象 | 每条都来自真实事故 | `rubric.json` |
| 难度倾斜权重 w=p(1-p)² | 把测量精度分配到难处 | 加分项加权 | `rubric.json` |

### 两条最关键的思想

**1. 能力指标 vs 状态指标**

```
8/8 全绿          = 状态指标（当前这批关卡没被抓到问题）
变异体杀灭率 78%  = 能力指标（红线有能力抓住 78% 的已知缺陷类型）
```

状态好但能力差 = 运气好。运气会用完。

**2. 可逆变异的巧妙之处**

变异的**逆操作就是标准答案**。这意味着不需要任何人工标注，就能得到带真值的回归集。
GameXpert-Bench 靠这个机制在零标注成本下构造了大规模评测集，我们靠它零成本得到了 15 个回归用例。

## 三、六个脚本各自回答什么问题

### `evidence.js` —— 证据够不够格
```bash
node tools/bench/evidence.js audit
node tools/bench/evidence.js check PD.simulateRuntime PD.solveLevel
```
四类伪证：
1. **注释说做了** —— 所以检查前必须 `stripComments()`
2. **死代码里做了** —— 函数定义了但没有任何可达调用点
3. **配置项做了** —— `ENABLE_X = false` 且没人读它
4. **我自己说做了** —— 口头声明

> 本次落地过程中，这个脚本第一次运行就抓住了**我自己**的伪证② ——
> 我加了 `PD.simulateRuntime` 却没让任何生产代码调用它。
> 连实现者本人也需要被这条规则约束。

### `parity-audit.js` —— 口径有没有分裂
```bash
node tools/bench/parity-audit.js 30 3
```
三层：
- **L1** 静态锚点扫描（R1~R9 铁律是否还在代码里）
- **L2** 重复实现探测（元检查：规则有没有又被复制成 N 份）
- **L3** 单向蕴含验证

L3 的判据必须是**单向蕴含**，这是本次审计最重要的认知修正：

```
solveLevel 判不可解  ⟹  运行时必然不可解     ← 上界成立，必须满足
solveLevel 判可解    ⇏  运行时可解           ← 先知比人强，落差是正常难度
```

第一版审计错误地比较了两者的**数字是否相等**，报出"3 类口径分裂"。
但 `solveLevel` 有三条**先知特权**（可从整个队列挑车、自动绕开 ghost、车位可压缩），
它的 `peakSlots` 恒接近 1 是**设计内行为**。要查的是蕴含有没有被违反，不是数字是否一致。

### `gate-audit.js` —— 红线有没有能力
```bash
node tools/bench/gate-audit.js 12 2
```
三种判定，缺一不可：
- `KILLED` —— 红线炸了，有效
- `SURVIVED` —— 红线没反应，是**盲区**（已声明的除外）
- `无法判定` —— 期望判据在基线就已经红了，**测不了**

> 第三种是首跑时发现必须加的。第一版把"测不了"算成"没抓住"，
> 得出「杀灭率 6.7%」这个严重失真的数字。
> **失真的指标比没有指标更危险 —— 它会把精力引到错的地方。**

### `strict-curve.js` —— 难度曲线的形状
```bash
node tools/bench/strict-curve.js 20 3
```
- **Strict** = S(τ) 在 τ∈[90,100] 的平均高度。判据 ≥70%
- **Cliff** = 老手胜率 − 随手胜率。健康区间 15~45
- **断崖检测** = 连续 ≥3 关老手胜率 <50%
- **锯齿检测** = 胜率突升 >50pp 的次数

为什么不看平均胜率：平均 78% 可能是"每关稳定 78%"（健康），
也可能是"前 20 关 100%、后 10 关 22%"（断崖，玩家在第 21 关集体流失）。
两者平均值完全相同，产品后果天差地别。**平均值把分布压成了一个点，而流失恰恰发生在形状里。**

### `mutators.js` / `sandbox.js` —— 变异算子与隔离加载
`sandbox.js` 用 `vm` 在隔离上下文里加载源码字符串。
必须隔离的原因：`require()` 有模块缓存，同一进程内无法加载同一文件的两个不同版本。
且变异体**只存在于内存**，绝不落盘 —— 落盘再跑一旦中途崩溃就留下被污染的源码。

### `bench-all.js` —— 一条命令
```bash
node tools/bench/bench-all.js 20 3
```
必须有一条命令的原因：六个脚本分开跑时，人会本能地只跑"上次报错那个"，
逐渐退化成"只看自己关心的那条红线"。这是红线体系失效的标准路径。

## 四、本次落地当场抓到的四类事故

### 事故 1：真机规则被实现了五遍（根因级）

已知坑 10 记录的现象是"求解器全绿但真机 56% 死局"，但根因不是某个算法写错了，而是**规则本身被复制成了五份**：

```
pd-core/solveLevel  ·  pd-game 运行时  ·  tools/validate-levels/simRuntime
tools/winrate/playOnce  ·  pd-levelgen/refPlay
```

改一条规则要同步五处，漏一处就是假绿灯。

**修法**：新增 `PD.simulateRuntime` 作为真机规则唯一权威实现，`parity-audit` L2 静态检查有没有人又偷偷重写。

L2 首跑查出 **16 个 tools 文件**带手写模拟器（`winrate.js`、`verify-curve.js`、`verify-lv2.js`、`verify-landed.js` 是活跃门禁，优先迁移）。

### 事故 2：验收脚本比真机宽松（假绿灯）

`validate-levels.js` 的 V1 调的是 `simRuntime(lv, true)`，`autoRelease=true` 意为「该色清空即放行」——
而 `pd-game.js:995` 已明确删除这条通道。

**验收标准结构性地比真机宽松 → 8 条红线全绿但玩家会卡死。**

**修法**：删掉本地 89 行重复实现，改为 25 行薄封装转调 `PD.simulateRuntime`，不传 `autoRelease`。

### 事故 3：V2 是过期红线（假红灯）

V2 判据是 `min(S_color) <= 0` 报错，实测 89/90 爆红，S 区间 `0.0% ~ 0.0%`。

探查 `LG.difficulty(n)` 发现所有关卡 `S === 0` —— 这是**现行设计的主动选择**：
每色总容量 ≡ 豆数，让「装满即离场」成为唯一正常通道。

**判据与设计相互矛盾 → 永久爆红。**

> **假红灯比假绿灯更难治。**
> 假绿灯只是漏掉一个问题；假红灯会训练所有人**忽略红线**，
> 而这个习惯会蔓延到旁边那些真正重要的红线上。

**修法**：语义校准为 `S < -1e-9`（负冗余 = 数学上不可通关）。

### 事故 4：审计工具自己也有假红灯

`evidence.js` 报告 `PD.simulateRuntime` 是死代码 —— 但它已经被 `validate-levels.js` 调用了。
原因：`readAll()` 只扫 `package/js/`，没扫 `tools/`。

**判据代码也是生产代码，也会有口径 bug。**

## 五、当前基线（2026-08-31 实测）

### 已修复
- ✅ 口径单一真值源已建立（`PD.simulateRuntime`）
- ✅ parity L3 三项蕴含检查全绿（89 样本，P1/P2/P3 = 0）
- ✅ V2 语义校准，不再永久爆红
- ✅ 契约符号 5/5 可准入

### 待修（按优先级）

**P0 —— 阻塞一切测量**

> **S=0 与广告变现通道数学冲突（本次审计最重要的发现）**
>
> 实测数据：
> | 关 | 豆数 | 总容量 | S | 结果 | clears |
> |---|---|---|---|---|---|
> | 1 | 360 | 360 | 0 | ✅ | 0 |
> | 6 | 434 | 434 | 0 | ❌ 剩 424 | 4 |
> | 7 | 452 | 452 | 0 | ❌ 剩 36 | 4 |
> | 16 | 496 | 534 | 38 | ✅ | 0 |
>
> **广告清车会销毁整辆车的剩余容量。S=0 时任何一次 clear 都让关卡数学上不可通关。**
> 凡 `clears > 0` 的关必死 —— 变现通道（看广告清车）与零冗余设计直接冲突。
>
> 连带后果：V1 42/90 不可解 → 基线 V1 常红 → 变异体杀灭率大量算子落入"无法判定"。
> **这一条不修，红线能力就测不出来。顺序不可逆。**

**P0 —— 策略深度为零（已量化）**

> Cliff = 0.0，且老手/随手两档画像逐关 `ok/carMoves/clears` **逐位相同**。
>
> 根因同样是 S≡0：每色总容量恒等于豆数 ⟹ 每辆车必然恰好装满 ⟹ **挑哪辆车在终局上完全等价**。
> **策略维度在数学上被消灭了。** 这正是用户原话「这还有策略么？」的量化根因。
>
> ⚠️ 修它必须动 S 契约（给出正冗余，让"装不满就变僵尸"成为真实代价）。
> 继续给模拟器加参数是无效的 —— 已实测两轮（资源参数、决策参数）均为 0 落差。

**P1**
- 难度曲线断崖：第 5~7 关连续老手胜率 <50%；锯齿 4 处
- V5 图案重复率 54.4%（判据 ≤5%）
- 16 个 tools 文件的手写模拟器待迁移

**已声明盲区（知道自己不知道）**
- M13 容量均分 / M14 队列严格轮转 —— 破坏的是"策略性/信息量"，当前**没有任何红线在量化这件事**

## 六、上线前必须做的事

```bash
node tools/bench/bench-all.js 20 3
```

退出码 0 才允许 `ksmg upload`。

**修复顺序不可颠倒**（按 `failure-taxonomy.md` 的先验概率）：

1. **C6 语法** —— 真机白屏，本地 Chrome 看不出来，先验概率最高
2. **C3 证据** —— 伪证会让后面所有结论失效
3. **C1/C2 口径** —— 口径不一致时，其他红线的数字都不可信
4. **C4 红线** —— 口径修好后再看关卡本身质量
5. **C5 杀灭率** —— 最后测能力，基线必须先全绿

> 不要倒着修。先修 C5 是徒劳的 —— 基线红着的时候，大量算子会落入"无法判定"，那个数字没有意义。

## 七、三条通用教训

1. **同一假设连续两次改参数都无效时，该怀疑的是假设本身，而不是参数还没调对。**
   Cliff=0 的排查过程：改资源参数无效 → 改决策参数无效 → 才去验证"两者输出是否真的不同" → 发现逐位相同 → 找到 S=0 这个真根因。

2. **失真的指标比没有指标更危险。**
   杀灭率 6.7% 会把人引向"补 12 条红线"，而真正该做的是"先修基线的 V1"。

3. **假红灯比假绿灯更难治。**
   假绿灯漏一个问题；假红灯毁掉整个红线体系的可信度。
