二、正确的模型：三层分离

旧做法把「可行性 / 难度 / 体验」揉成一个胜率数字，导致旋钮互相污染。必须分层。

A 层 · 可行性 Feasibility

布尔量，不是概率。
∃π 使 π 能清空

不可解 = bug，不是「很难」。
生成器唯一必须保证的事。

当前正确

B 层 · 难度 Difficulty

决策树的宽度与深度，与策略无关。

T 容错率 = 安全步/可选步
D 陷阱深度 = 犯错到暴露的延迟
M* 最优步数（只管时长）

当前 T≡1 无难度

C 层 · 体验 Experience

才是概率层，且必须跨策略稳定。

自检红线：
max(策略) − min(策略) < 15%

上轮缺此自检

T · 容错率的几何含义

D · 陷阱深度＝用户校准的语义

「他如果过早的放上去 可能就浪费了一个坑位
他是有关联关系的 比如在某些颜色移除后才出现」

D 越大越难，但太大会让玩家觉得「莫名其妙就输了」 —— 洋葱壳的作用就是让 D 可预见。

四、难度的唯一真实来源：缓冲区压力 P

这类游戏的数学本质是受限缓冲区调度（bin packing + 拓扑排序）。难度只来自一个比值：

P = (同时需要在场的颜色数) / (可用车位数)

P < 1  →  所有需要的颜色都能同时在场  →  必胜，零难度
P = 1  →  正好在必胜边界
P > 1  →  必须排序，排错就浪费坑位  →  有难度

当前处境

C = 6色数（我上轮封顶）
S = 6车位（第6格广告解锁）
P = 6/61.00

正好压在必胜边界上 —— 这是「随便就能过」的数学根因。

P 与难度的关系

色数必须显著超过车位数才有难度。而我上一轮把色数封顶在 6，恰恰锁死了唯一有效的难度旋钮 —— 当时我以为「ghost 需要一个场上没有的颜色」是硬约束，现在看这个约束本身就是设计缺陷：它把 C 和 ghost 机制耦合了。

五、为什么失败状态不可达（机制层证明）

先说清楚：惩罚机制是做对了的。实测确认「车装不满就永远占位」真实生效（4/4 分支里 3 个会变僵尸）。 问题不在「没有惩罚」，而在「惩罚可以无代价撤销」。

真机判死条件

function checkStuck() {
  if (anyMovable()) return;               // 有豆能走 → 活
  if (freeSlots() > 0 && queueCount())
      return;   // ← 有空位就不死
  S.phase = 'dead';
}

必输的唯一路径：车位全满 且 全是僵尸 且 队列还有车。

三道免死闸

  • 闸 1：玩家可主动不填满车位 → 第一条 if 永不通过
  • 闸 2：tow 广告可拖走任意僵尸车（无限次）
  • 闸 3：clear 消除 / refresh 刷新 / revive 复活
rewardAd('tow', function(){
  departCar(i);            // 无限次撤销
  toast('僵尸车已拖走！');
});

七、三个方案（需你定）

方案 1 推荐

车位是唯一资源，不可无损回收

  • 判死改为：无豆可走 且 队列有车 → 死（去掉「有空位就不死」）
  • tow 保留但每关限 1 次
  • T 立刻从 1.0 掉到真实值

代价：手感变紧，需重调所有关卡

方案 2

放车次数上限

  • 每关给 M_max = M* + k
  • 用完还有豆 → 输
  • 语义完全对应「过早放上去浪费坑位」

改动最小；缺点是暴露最优步数信息

方案 3

不做失败，改做星级

  • 保留必胜，难度体现在 3 星门槛
  • 最符合休闲 IAA，不卡人、广告位全保留

与你「目标就是要难」可能不符

八、新的难度契约：按 (T, D) 定义
