# 全类型关卡批量生成规则

> 适用于「老铁眼真尖」全部关卡的单关、批量和新主题策划。  
> 目标：一次识别玩法类型、生成范围、固定文档格式和后续配置结构，避免把单图异常、双图找不同、寻物和连续剧情混为一谈。

## 1. 支持的关卡类型

| `mode` | 中文玩法 | 核心判断 | 场景字段 | 当前配置特征 |
|---|---|---|---|---|
| `hidden` | 单图找异常 | 找出不属于时代、场景或常识的异常物 | `scene` | `odds` 为异常物；历史关卡可能省略 `mode` |
| `spot` | 双图找不同 | 对照两张同构图片，找右图新增或变化之处 | `sceneA`、`sceneB` | 必须显式 `mode: "spot"`，可带 `layout` |
| `hunt` | 单图寻物 | 在复杂场景中找指定物品 | `scene` | 必须显式 `mode: "hunt"` |
| `story` | 连续剧情搜证 | 找证据并推进跨关剧情 | `scene` | 含 `intro`、`briefGoals`、`epilogue`、`narrative` 等剧情字段 |

`boss`、`bossStage`、`diff` 和 `layout` 都是玩法修饰，不单独算一种关卡类型。

## 2. 一键识别顺序

生成前必须按以下顺序判断，只命中一种主玩法。

### 2.1 第一优先级：用户或配置明确指定

- 用户写出 `mode` 时，直接采用该值。
- 已有关卡含 `sceneA + sceneB` 时，识别为 `spot`。
- 已有关卡含 `mode: "story"`，或同时出现章节、开场、通关揭示、玩家旁白时，识别为 `story`。
- 修改现有主题时，以该主题当前 `mode` 为准，不因一句“找茬”擅自换玩法。

### 2.2 第二优先级：需求语义

- “找不同、左右图、上下图、A图B图、多出来、变化处” → `spot`。
- “寻物、找物品、物品清单、藏起来的东西、在场景里找指定物” → `hunt`。
- “穿越物、时代错位、不合常理、单图找茬、异常物” → `hidden`。
- “剧情、剧本、章节、连续故事、搜证、旁白、反转” → `story`。

### 2.3 第三优先级：无明确关键词时的默认

- 明确要求两张对照图 → `spot`。
- 明确给出要寻找的正常物品清单 → `hunt`。
- 只说“单图找茬”或“批量生成找茬关卡” → `hidden`。
- 存在跨关人物关系和连续因果 → `story`。
- 不得在同一关混用两种 mode；难以判断时，在生成文档的“主题定位”中写明本次推定的唯一玩法。

## 3. 生成范围识别

依次识别以下范围：

1. **单关**：用户指定一关或一个明确场景。
2. **连续关卡**：用户指定关卡区间，如“6-10关”。
3. **完整批次**：用户指定数量，但未指定编号；从现有主题最后一关继续编号。
4. **新主题**：用户给出新主题名或要求“换个主题”；先建立统一主题定位，再批量生成。
5. **整部故事**：仅 `story` 使用，按章节连续生成。

编号规则：

- 文档中的显示关卡号在主题内连续。
- 配置中的 `idx` 必须全局唯一，但策划文档不填写 `idx`。
- 未指定批次数量时：非故事型默认先产出5关供确认；故事型默认每章5关。
- 修改现有批次时，保留原关卡编号、标题层级和未点名内容。

## 4. 非故事型关卡固定 Markdown 格式

`hidden`、`spot`、`hunt` 一律使用本节格式。不得因玩法不同改变标题层级和字段顺序，只替换“目标清单”中每条目标的说明内容。

```markdown
# 《<主题名>》<玩法中文名>关卡设计

## 主题定位

- 玩法模式：<hidden / spot / hunt>。
- 核心体验：<一句话说明玩家在找什么>。
- 场景范围：<地点、年代或世界观>。
- 美术方向：<统一构图和风格>。
- 关卡数量：<本批次关卡数>。
- 难度曲线：<从教学到高潮的变化>。

---

## 第<关卡号>关：<关卡名>

### 关卡目标

<一句玩家能看懂、但不过度泄露具体位置的目标描述。>

### 场景设计

<描述地点、时间、人物或环境、前中后景层次和主要视觉动线。>

### 目标清单

1. **<目标名称>**
   - 画面表现：<物体或差异在画面中的自然表现>。
   - 隐藏方式：<同色伪装、透视缩小、生活化遮挡或视觉干扰>。
   - 难度：<易 / 中 / 难>。

<按本关目标数量继续编号。>

### 难度设计

- 目标数量：<数量>。
- 难度档位：<教学 / 简单 / 普通 / 困难 / 地狱 / 解压>。
- 分布要求：<说明前中后景、左右和高低区域如何分散>。
- 建议时长：<由项目时长公式计算的秒数>。

### 生图约束

- <本关必须保留的构图、人物和物件>。
- <本关禁止出现的文字、错误物件和额外答案>。
- <玩法专属的成图一致性要求>。

### 通关反馈

<一句简体中文反馈；hidden 解释异常，spot 概括变化，hunt 呼应主题。>

---
```

### 4.1 `hidden` 的目标清单写法

每条目标写一个异常物：

- **目标名称**：玩家找到后显示的简体中文名称。
- **画面表现**：物体应自然放在场景中，说明为什么看起来合理。
- **隐藏方式**：说明视觉伪装，不写错误坐标。
- 关卡目标应说明时代或场景边界，但不直接列出全部答案。
- 通关反馈解释该物为何不属于当前年代、地点或常识。

### 4.2 `spot` 的目标清单写法

每条目标写一个差异：

- **目标名称**：右图新增、缺失、变色、变形或换位的内容。
- **画面表现**：同时写清 A 图原状和 B 图变化后的状态。
- **隐藏方式**：利用环境复杂度和视觉相似度，不得用错位构图制造假难度。
- A、B 两图必须同尺寸、同机位、同透视、同人物姿态、同光线和同主体布局。
- 除目标清单列出的差异外，不允许出现模型随机漂移形成的额外差异。
- 标注坐标统一对应游戏判定图（当前为 `sceneB`）。

### 4.3 `hunt` 的目标清单写法

每条目标写一个需要寻找的正常物品：

- **目标名称**：简体中文物品名，必须与画面实物一致。
- **画面表现**：说明它如何自然融入生活场景。
- **隐藏方式**：允许同色、局部遮挡和景深变化，但主体必须可辨认。
- 每个目标默认只出现一次；需要找多个同类物品时必须明确数量。
- 不把所有目标放在同一桌面、柜子、箱子、抽屉或画面四角。

## 5. `story` 固定路由

识别为 `story` 后，不使用第4节的非故事模板，必须完整阅读并执行：

`docs/故事型关卡剧本生成规则.md`

输出格式严格参考：

`docs/《1808房间》第一章1-5关剧本.md`

故事型关卡必须先确定故事圣经、章节节奏和逐关信息增量；开场只给3条模糊调查方向，不公布答案名。开场正文、通关揭示和下一关钩子分别不得超过40个可见字符，其中开场与通关揭示必须为单段且不得手动换行。

## 6. 批量难度曲线

未收到用户明确数量和难度时，按批次位置生成：

| 玩法 | 教学/前段 | 中段 | 后段/高潮 | 当前项目可用范围 |
|---|---:|---:|---:|---:|
| `hidden` | 1-3个 | 4-5个 | 6-7个 | 1-7个 |
| `spot` | 3个 | 4-5个 | 6-7个 | 3-7个 |
| `hunt` | 3个 | 4-6个 | 7-8个 | 3-8个 |
| `story` | 5-6条 | 6-7条 | 7-9条 | 依故事规则 |

数量不是唯一难度来源。每关还必须满足：

- 至少保留1个较明显目标，避免纯猜。
- 每条目标只能对应一个唯一答案物体和一个点击区；禁止同一目标重复出现、拆成多个答案或配置多个热区。
- 约60%的目标使用同色伪装、透视缩小、生活杂物干扰或部分遮挡。
- 目标分布在前景、中景、后景以及不同高低区域。
- 不得全部集中在同一容器、家具、人物身上或四角。
- 任意两个答案物体和标注热区不得相交、包含或重叠。
- 不用超小热区、错位热区、完全遮挡、过暗或模糊制造难度。
- `spot` 的难度来自合法差异和视觉搜索，不来自两图整体不一致。

时长不得凭感觉填写。图片和目标数量确定后，调用项目现有 `M3.suggestDuration` / `M3.audit` 规则计算；`boss` 只增加阶段压力，不改变 mode。

## 7. 通用文案与生图规则

- 所有玩家可见文字只能使用简体中文和阿拉伯数字。
- 图片中禁止英文、日文、繁体字、拼音、乱码和真实品牌标志。
- 关卡名不超过8个汉字，不把“困难、地狱、BOSS”等难度词写进标题。
- 内部 `prop` 使用稳定、唯一的英文标识；玩家可见 `tag` 必须是简体中文。
- 必须满足「目标数 = 唯一答案数 = `odds.length` = 点击区数」；同一关的 `prop` 不得重复，一个 `odds` 只能包含一个点击框。
- 同一主题保持统一画幅、画风、人物设定、色彩逻辑和世界观。
- 人物不是每关必需，但一个批次不能每关都没有人物；人物不得遮挡答案。
- 不先生成一堆随机图片再倒推答案。必须先完成关卡设计和目标清单，再生图。
- 成图涉及文字时，提示词必须逐字指定需要出现的简体中文；不需要文字时优先无文字。

## 8. 从策划文档到配置的映射

策划 Markdown 不写坐标、`idx` 或 JSON。成图通过审核并完成标注后，再映射到统一 `levels-config.json`。

### 8.1 通用字段

- `idx`：全局唯一数字。
- `themeId`：主题编号。
- `mode`：`hidden` 历史数据可省略，新关卡建议显式填写；其余模式必须填写。
- `title`：`第N关 · 标题`。
- `duration`：由时长规则计算。
- `hint`：玩家目标提示，数量必须与 `odds.length` 一致。
- `diff`：难度、点击容差、误点惩罚和奖励。
- `odds`：标注完成后的答案数组。

### 8.2 模式专属字段

- `hidden`：`scene`；`odds` 至少含 `prop,x,y,w,h`，需要显示名称时含中文 `tag`。
- `spot`：`sceneA,sceneB,layout`；`odds` 至少含 `x,y,w,h,tag`。
- `hunt`：`scene`；`odds` 含 `prop,x,y,w,h,tag`。
- `story`：除 `scene` 和完整 `odds` 外，还含 `storySchema,chapterTitle,intro,briefGoals,epilogue,epilogueTag`；每条证据含 `clue,narrative`。

所有模式均执行唯一映射：一条策划目标只生成一条 `odds`，一条 `odds` 只定义一个矩形点击区。多部件物体使用一个完整包围框，不得拆成多个点击区。

每个新主题仍使用同一个 `levels-config.json` 下发。换主题时应优先新增配置和资源，不为相同 mode 复制一套游戏引擎代码。

## 9. 一键生成流程

1. 识别玩法：显式 mode > 现有配置结构 > 需求关键词 > 默认规则。
2. 识别范围：单关、区间、批次、新主题或整部故事。
3. 读取现有主题，避免编号、答案名和场景重复。
4. 选择固定模板：非故事用本文第4节；故事用故事型固定模板。
5. 先生成主题定位、难度曲线和逐关目标，再写每关正文。
6. 做分布检查：目标不能扎堆、相交、全在容器里或全在四角。
7. 做文案检查：简体中文、标题长度、目标数量和玩法语义一致。
8. 用户确认策划文档后，才进入生图、双桶上传、编辑器标注和配置发布。

## 10. 输出前检查

- [ ] 已唯一识别 `hidden / spot / hunt / story` 中的一种。
- [ ] 已识别单关、区间、批次或新主题范围。
- [ ] 非故事型 Markdown 标题层级和字段顺序完全一致。
- [ ] 故事型已改走故事规则，未套用非故事模板。
- [ ] 目标数量符合模式范围和批次难度曲线。
- [ ] 目标分散在前中后景和不同区域，没有重叠或扎堆。
- [ ] 每条目标只对应一个唯一答案和一个点击区，目标数、唯一答案数、`odds.length` 与点击区数相等。
- [ ] `spot` 除指定差异外两图完全一致。
- [ ] `hunt` 的目标都自然融入场景且默认只出现一次。
- [ ] `hidden` 的每个异常都有明确的不合理原因。
- [ ] 标题和所有玩家可见文字均为简体中文。
- [ ] 策划文档没有坐标、`idx`、JSON 或上传发布操作。
- [ ] 用户确认后才进入生图、标注和统一配置下发。
